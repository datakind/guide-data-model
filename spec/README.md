# `spec/` — the installable GUIDE Data Model specification

This directory holds the parts of the GUIDE Data Model that are designed to be *consumed by machines*: the generated PostgreSQL DDL. Human-readable documentation lives in [`../docs/`](../docs/).

## Source

The SQL is generated from the **`Objects`** object of [`../guide_data_model_schema_v1.0.0.json`](../guide_data_model_schema_v1.0.0.json) (`sheets.Objects.records`), which defines **500 objects**, **7,943 columns**, and **1,818 foreign-key reference rows** across 11 entities. Table comments come from `sheets.ObjectDesc.records`.

## Contents

```
spec/
└── sql/                        PostgreSQL DDL to install the data model
    ├── install.sql             Master script — runs everything in order, in one transaction
    ├── 001_create_schemas.sql  One PostgreSQL schema per entity (11)
    ├── tables/                 One file per entity (11 files, 500 tables)
    │   ├── 01_core.sql
    │   ├── 02_person.sql
    │   ├── ... (and so on)
    │   └── 11_admissions.sql
    ├── 003_foreign_keys.sql    1,781 enforceable FK constraints
    ├── 004_indexes.sql         1,200 indexes on FK columns
    └── teardown.sql            DROP everything
```

## How to install

You need **PostgreSQL 14 or newer** (tested on PostgreSQL 16).

```bash
createdb guide-data-model
psql -d guide-data-model -f spec/sql/install.sql
```

`install.sql` stops on the first error and wraps the install in a single transaction. It includes its component files with `\ir`, so it can be run from any working directory.

To start over:

```bash
psql -d guide-data-model -f spec/sql/teardown.sql
psql -d guide-data-model -f spec/sql/install.sql
```

## What's in the generated SQL (1.0.0)

- **500 tables** in 11 PostgreSQL schemas, one per entity: `core` (36), `person` (61), `engagement` (31), `academics` (199), `appointment` (8), `advising` (17), `finances` (37), `learner_success` (1), `supports` (60), `workforce` (33), `admissions` (17)
- **1,781 enforceable foreign-key constraints** (1,131 across schemas, 650 within a schema)
- **1,200 indexes** on non-primary-key FK columns (primary keys are indexed automatically)
- `COMMENT ON` for every table and every column that has a description in `Objects` (7,943 columns)

Names are converted from PascalCase to snake_case (`CourseLookup` → `course_lookup`). Identifiers that are PostgreSQL reserved words get an `_x` suffix; identifiers longer than 63 characters are truncated with a short hash.

### How foreign keys are built

`FKReference` usually names only the referenced business identifier (e.g. `ActivityLookup.ActivityIdentifier`) even though the target's primary key is tenant-scoped (`TenantIdentifier`, `ActivityIdentifier`). The generator adds the remaining primary-key columns — normally `TenantIdentifier` — from the source table, so every constraint covers the full target key and keeps references inside one tenant.

Of the 1,818 FK reference rows:

| Outcome | Rows |
| --- | ---: |
| Emitted as a constraint | 1,781 |
| Duplicate of an emitted constraint | 4 |
| Skipped: target is a revisioned table and the source has no `RevisionIdentifier` | 33 |

The 33 skipped references are listed at the end of [`sql/003_foreign_keys.sql`](sql/003_foreign_keys.sql). They point at `Assessment`, `Competency`, `AssessmentItem`, `LearningResourceLookup`, and `LearnerDegreePlan`, whose primary keys include a `RevisionIdentifier`.

### How defaults are translated

`Objects` records defaults in SQL Server syntax. The generator translates them:

| Model default | PostgreSQL |
| --- | --- |
| `SYSUTCDATETIME()` | `DEFAULT CURRENT_TIMESTAMP` |
| `NEXT VALUE FOR [dbo].[SEQ_…]` on an integer column | `GENERATED BY DEFAULT AS IDENTITY` |
| `NEXT VALUE FOR …` on a text identifier | no default (identifiers are assigned by the loading process) |
| `0` / `1` / `True` on a boolean | `DEFAULT FALSE` / `DEFAULT TRUE` |
| `N'Active'` | `DEFAULT 'Active'` |

## Validation

The DDL is checked in four ways:

1. **Structural** — every table has a primary key, no duplicate columns within a table, every FK resolves to an existing target table and column with a compatible type, and `install.sql` loads every generated file in order inside a transaction.
2. **PostgreSQL identifier rules** — every schema, table, column, constraint, and index name is a legal identifier (at most 63 characters, not a reserved word).
3. **SQLite execution** — translated to SQLite-compatible syntax and executed in memory as a fast syntax check.
4. **PostgreSQL install** — installed into a temporary PostgreSQL cluster, counts of tables, foreign keys, and indexes checked against the generated files, then torn down.

```bash
python scripts/validate_sql.py        # checks 1–3, no PostgreSQL needed
python scripts/validate_postgres.py   # check 4, needs initdb, pg_ctl, createdb, psql
```

`validate_postgres.py` must not run as the `root` user (PostgreSQL refuses to). If `initdb` and `pg_ctl` are not on your `PATH` — Debian and Ubuntu install them under `/usr/lib/postgresql/<version>/bin` — set `PG_BIN` to that directory.

## How the SQL is generated

The SQL is **generated**, not hand-written. To regenerate after the model changes:

```bash
python scripts/generate_schema.py guide_data_model_schema_v1.0.0.json
```

With no argument the script reads `guide_data_model_schema_v<VERSION>.json` from the repository root. It is idempotent: it overwrites everything under `spec/sql/` and the per-entity Markdown under `docs/data-model/entities/`.
